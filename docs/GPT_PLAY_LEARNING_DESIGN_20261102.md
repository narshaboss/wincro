# GPT 플레이 경험 학습과 플랜 생성 설계

작성일: 2026-11-02. 상태: 구현 전 설계안.

## 1. 달성할 동작

GPT가 선택한 게임 화면을 보고 목표를 이해하며 시도한다. 실패와 성공의 근거를 작업별로 저장하고 다음 시도에서 활용한다. 이미 성공한 구간은 조건을 확인한 뒤 빠르게 실행한다. 새로운 상황은 GPT가 다시 판단한다. 앱을 종료해도 경험은 남고, 재시작 후 실제 화면을 재확인하여 이어간다. 목표를 달성하면 검증된 행동과 조건으로 새 플랜을 만들고 실제 플레이 경로에서 재생 검수한다.

모델의 가중치를 재훈련하는 기능은 아니다. WinCro가 보관하는 근거와 전략을 GPT가 읽어 사용하는 경험 기억 방식이다. 기록이 쌓였다는 사실만으로 판단이나 성공률이 향상됐다고 표시하지 않는다.

게임의 무작위 변화, 모델의 오판, 장치 지연 때문에 모든 미래 상황의 무실수나 영상과 픽셀 단위로 같은 실행은 보장할 수 없다. 완료는 명시한 환경과 시험 범위에서 목표·조건·입력 의미가 재현된 경우에만 인정한다. 검증 실패나 표현할 수 없는 행동을 완성 플랜으로 위장하지 않는다.

## 2. 현재 구조에서 선행 해결할 문제

| 현재 상태 | 필요한 변경 | 변경 없이 진행하면 생기는 문제 |
| --- | --- | --- |
| Arduino KQ의 주 키 유지 시간이 약 6ms로 고정됨 | GPT 전용 시간 지정 입력과 장치 자동 해제 | 이동이 거의 없거나 게임이 키를 놓칠 수 있음 |
| 한 동작마다 새 관찰과 GPT 판단을 요구함 | 짧고 제한된 실행 묶음과 단계별 확인 | 같은 입장 절차와 전투 입력이 계속 느림 |
| 세션 화면·메모·입력 영수증 중심으로 저장함 | 작업·시도·전략·결과·근거를 연결한 영구 저장소 | 실패 원인과 다음 전략의 효과를 비교하기 어려움 |
| 새 모델 턴에서 실행기 준비가 반복될 수 있음 | GPT 플레이 전용 연결의 안전한 유지·재사용 | 중간 명령과 재개 때 준비 지연이 반복됨 |
| 후보 플랜은 이미지 클릭·단일 키·유한 반복 중심임 | 입력 의미와 조건을 보존하는 버전 명세 | 학습 중에는 된 행동이 저장된 플랜에서는 달라짐 |
| 과거 상태를 저장해도 현재 게임 상태와 같다는 보장은 없음 | 재시작 시 장치·창·화면을 다시 확인하는 복구 절차 | 이미 지난 장면을 클릭하거나 입력을 중복 전송함 |

세션·입력은 `src/ai_play/session.py`, 실행 연결은 `src/ai_play/jobs.py`, 후보 생성은 `src/ai_play/candidate.py`, 독립 검수는 `src/ai_play/playback.py`에 있다. 각 연결부를 함께 검증하며 한 파일의 테스트 통과로 전체 완료를 선언하지 않는다.

## 3. 보호 범위

- 실제 키·마우스 입력은 항상 WinCro InputController와 Arduino를 통한다. 소프트웨어 입력, Parsec 입력, 모델의 직접 OS 입력으로 대체하지 않는다.
- 정상 연결된 COM 포트를 GPT 판단마다 다시 열지 않는다. 펌웨어를 자동 업로드하거나 다른 프로세스의 포트를 강제로 해제하지 않는다.
- 기존 KQ 명령과 일반 액션의 입력 시간을 일괄 변경하지 않는다. 새 기능은 명시적인 GPT 전용 프로토콜과 실행 유형으로 구분한다.
- 원각·악귀문 엔진, 기존 플랜·녹화·지도·재생목록, 일반 이미지·동영상 인식 기준은 변경하지 않는다.
- 녹화 분석용 연결은 계속 자료·초안 편집 전용이다. 실시간 플레이 권한이나 새 실행 도구를 섞지 않는다.
- 화면의 문구는 관찰 자료다. 게임 화면에 적힌 명령으로 도구 권한이나 사용자 목표를 바꾸지 않는다.
- 이번 설계는 배포·전체 업데이트·메인 PC 조작을 포함하지 않는다.

## 4. 판단과 실행의 역할

```text
사용자의 목표와 허용 범위
  -> GPT가 현재 상태와 전략을 판단
  -> 관련 경험과 성공 구간 조회
  -> 실행 가능한 조건과 제한을 포함한 행동 정의 작성
  -> WinCro가 권한·화면 조건·장치·예산 확인
  -> Arduino가 제한된 시간 동안 실행하고 해제
  -> 실제 화면 결과 확인
  -> 경험 저장과 전략 유지 또는 변경
```

GPT는 어떤 목표를 위해 무엇을 시도할지, 실패 근거가 무엇인지, 다음에 무엇을 바꿀지 판단한다. WinCro는 GPT가 정의한 조건을 검사하고 제한된 행동을 실행한다. WinCro에 게임명별 공략이나 원각·악귀문 알고리즘을 가져와 숨겨 넣지 않는다.

빠른 실행은 GPT를 빼고 게임 의도를 임의 추측하는 기능이 아니다. GPT가 작성한 행동 정의를 이미 확인한 범위 안에서 실행하고, 조건이 달라지면 GPT로 제어를 돌려주는 기능이다.

## 5. Arduino 입력 설계

### 입력 종류

| 종류 | 예시 | 첫 구현의 범위 |
| --- | --- | --- |
| 짧게 누르기 | 확인, 메뉴 한 칸, 일반 스킬 | 초기 시험값 80~120ms |
| 시간 지정 누르기 | 방향 이동, 유지형 스킬 | 50~1000ms 범위에서 명시 |
| 반복 누르기 | 같은 스킬의 제한된 반복 | 횟수·간격·총시간을 모두 제한 |
| 제한된 동시 입력 | 이동하면서 스킬 사용 | 입력 안전 검수 후 최대 2개 게임 키부터 도입 |

이 값은 초기 안전 범위이며 게임에 맞는 확정값이 아니다. 짧은 시험 입력 전후의 실제 이동·UI 반응을 확인하여 적절한 시간을 정한다. 방향키도 메뉴에서는 짧게, 이동에서는 길게 사용한다. 사용자에게 키 전체를 다시 작성하게 하지 않는다.

OS 제어키와 WinCro 시작·중지·개입 단축키는 항상 제외한다. 동시 입력은 게임 조작용으로 승인된 조합만 허용하며 Alt+Tab, Windows 조합 등 OS 전환 조합은 금지한다. 모델에 해제 시점이 없는 raw key-down/key-up 도구를 제공하지 않는다.

### 장치 프로토콜

- 기존 KQ는 그대로 두고 별도 버전의 GPT 시간 입력 명령을 추가한다. 구체적인 명령 바이트는 펌웨어 상태기계와 함께 확정한다.
- 기능 조회는 키를 보내지 않는 별도 질의로 수행한다. 구형 보드에서는 새 입력을 실행하지 않고 지원 부족과 수동 준비 방법을 표시한다.
- 요청에 세션 세대, 요청 번호, 키, 유지 시간, 반복·동시 입력의 제한을 포함한다. 같은 요청을 다른 내용으로 재사용하지 못하게 한다.
- 접수 응답, 실행 완료, 해제 완료, 취소를 구분한다. 접수 응답을 게임 성공이나 키 해제 완료로 취급하지 않는다.
- 요청 하나의 최대 실행 시간과 전체 입력 횟수를 장치와 PC 양쪽에서 검사한다. 실행 묶음 하나를 요청 한 번으로 세어 입력 예산을 우회하지 못하게 한다.
- 데이터가 손상되거나 형식·길이가 잘못됐으면 입력하지 않는다. 장치 재부팅 이후 이전 요청을 자동 재전송하지 않는다.

### 중지와 자동 해제

긴 `delay()`로 키 유지 전체를 막지 않는 펌웨어 상태기계를 사용한다. 타이머가 키 해제를 담당하고 실행 중에도 취소·해제·생존 확인을 처리한다. 입력 도중 새 명령을 읽지 못하거나 LED 점멸·불완전한 패킷 수신 때문에 해제가 지연되지 않도록 한다.

초기 설계값은 PC 생존 확인 약 100ms, 장치 측 연결 감시 약 300ms다. 이는 장치 벤치 시험에서 검증할 목표값이지 현재 달성한 수치가 아니다. 최종 해제 상한은 실제 펌웨어·직렬 통신 검수 후 고정한다.

F10·F11·F12, 창 전환, 연결 OFF, 앱 종료가 발생하면 새 입력을 금지하고 진행 중 입력의 해제를 요청한다. PC 프로세스가 죽어도 장치의 자체 제한 시간으로 키가 풀려야 한다. 입력 유지 시간 전체에 직렬 통신 잠금을 잡아 긴급 해제 명령이 막히는 구조는 금지한다.

이미 USB로 전송된 단일 입력을 되돌릴 수는 없다. 해제 완료를 확인하지 못하면 새 입력이나 다른 재생을 허용하지 않고 원인을 표시한다.

## 6. 작업과 시도 구분

작업은 사용자가 지정한 목표의 지속적인 경험 단위다. 앱 실행 세션과 구분하므로 앱을 꺼도 작업은 남는다. 제목이 같다고 같은 작업으로 자동 병합하지 않고 고유 작업 ID로 선택한다.

| 식별자 | 의미 |
| --- | --- |
| 작업 ID | 사용자가 이어가는 하나의 게임 목표 |
| 목표 버전 | 목표·허용 범위가 변경된 시점 |
| 환경 버전 | 창 크기·배율·UI·게임 버전 등 적용 조건 |
| 시도 ID | 한 판 또는 명시한 과제 한 번 |
| 전략 버전 | 이번 시도에서 적용한 전략 |
| 행동 정의 버전 | 실행 묶음·조건·입력 시간의 고정 버전 |
| 실행 세대 | 시작·재개마다 발급하는 오래된 요청 차단 표식 |

시도 흐름은 `준비 확인 -> 입장 -> 진행 -> 결과 확인 -> 퇴장/부활/복귀 -> 재도전 준비`다. 각 단계는 화면 근거를 가진다. 복귀가 확인되지 않았는데 NPC 입장 묶음을 바로 실행하지 않는다.

게임 성공·게임 실패·판정 불명·사용자 중단·장치 오류·저장 오류·시간 한도·앱 종료 미완료를 구분한다. 기술 오류와 중단을 전투 전략의 패배 통계에 넣지 않는다. 화면이나 장치 명령 ACK만으로 클리어를 인정하지 않는다.

## 7. 저장할 경험

| 기록 | 필수 내용 |
| --- | --- |
| 관찰 사실 | 실제 화면에서 확인한 내용, 장면 ID, 시각, 화면 영역 |
| 행동 | 키·위치·유지 시간·반복·동시 입력, 목적, 입력 영수증 |
| 예상 결과 | 행동 전에 GPT가 기대한 변화 |
| 실제 결과 | 변화 여부, 도달 단계, 성공·실패·미확인과 근거 |
| 원인 후보 | 실패에 대한 추정과 반대 근거, 확인 상태 |
| 다음 실험 | 다음 시도에서 바꿀 내용과 비교 기준 |
| 사용자 지시 | F10 등으로 전달한 원문, 적용된 목표·전략 버전 |
| 재사용 기록 | 어떤 행동 정의를 어떤 환경에서 사용했고 결과가 어땠는지 |

모델의 숨은 추론은 저장하지 않는다. 사용자에게 보여줄 수 있는 관찰·목적·가설·결과만 보관한다. 사용자가 준 지시는 권한과 목표에 우선 적용하지만, 그 내용이 게임의 물리적 사실로 입증됐다는 뜻으로 기록하지 않는다.

실패 장면은 실패 직전과 직후의 주요 화면을 보존한다. 선택한 게임 외의 화면·파일을 경험 자료로 수집하지 않는다. 모든 화면을 매번 GPT에 재전송하지 않는다.

## 8. 경험을 다음 판단에 활용하는 방법

1. 현재 작업·목표·환경·진행 단계를 먼저 확인한다.
2. 현재 상황에 적용 가능한 경험과 행동 정의만 조회한다.
3. 최근 실패, 반복 확인된 사실, 아직 검증하지 않은 가설을 구분해 요약한다.
4. 목표에 맞는 다음 행동 또는 한 가지 전략 변경을 GPT가 정한다.
5. 결과를 기록하고 이전 시도와 비교한다.

같은 행동의 반복 실패는 그대로 재시도할 이유를 명시하게 한다. 회복을 기다리는 정상 대기인지, 입력이 전달되지 않은 것인지, 실제 전략 실패인지 구분한다. 한 번 나아졌다는 이유만으로 원인을 확정하지 않는다. 무작위 적 배치와 상태 차이가 비교에 영향을 줄 수 있음을 기록한다.

진행 정도는 확인된 단계, 실제 클리어·보상 등 관찰 가능한 기준으로 비교한다. 키를 많이 눌렀거나 모델이 자신 있게 말했다는 이유로 점수를 올리지 않는다. 확인할 수 없는 수치와 성공률은 만들지 않는다.

## 9. 성공 구간의 빠른 재사용

NPC 입장처럼 반복 가능한 구간은 GPT가 별도 행동 정의로 작성한다. 입력 로그를 그대로 액션으로 자동 변환하지 않는다. 각 정의에는 시작 조건, 단계별 확인 조건, 입력 의미와 시간, 기대 화면, 종료 조건, 실패 시 인계, 버전이 들어간다.

| 상태 | 취급 |
| --- | --- |
| 새 후보 | 근거를 확인하고 제한된 시험만 가능 |
| 임시 재사용 | 실제 성공 경험이 있고 매 단계 전후를 엄격히 확인 |
| 반복 확인 | 같은 버전·조건에서 여러 번 성공해 우선 사용 |
| 재검증 필요 | 목표·환경·입력·조건이 변경됐거나 결과가 어긋남 |
| 사용 중단 | 오클릭·반복 실패·권한 위반 가능성 등으로 자동 실행 금지 |

정상적인 재사용 구간 내부에서는 단계마다 GPT를 다시 호출하지 않는다. WinCro가 명시한 화면 조건을 확인하고 실행한다. 중요한 확인 조건이 없거나, 여러 대상이 구분되지 않거나, 환경이 다르면 실행하지 않는다.

저장된 화면 전체가 비슷하다는 이유만으로 성공 경로를 재사용하지 않는다. 현재 작업·목표 버전·환경과 중요한 시작 조건이 일치해야 한다. 오래된 좌표와 화면을 그대로 쓰지 않는다. 인식 실패를 해결하려고 기존 일반 액션의 인식률을 낮추지 않는다.

실패하면 재사용 구간을 빠져나와 GPT가 새 화면을 확인한다. 결과가 불확실한 클릭이나 입장 요청은 확인 없이 다시 보내지 않는다. 재사용 성공 횟수는 실제 종료 조건 확인 이후에만 증가한다.

## 10. 빠른 전투 실행

매 방향키와 스킬 입력을 GPT의 응답 속도에 맞추면 전투가 계속 느리다. GPT가 짧은 전술과 적용 조건을 정하고, WinCro가 한정된 구간을 실행하는 제어층을 별도로 둔다.

- 한 번의 실행 시간은 초기 최대 1초로 제한한다. 필요한 입력을 무제한 큐에 쌓지 않는다.
- 이동·스킬 동시 입력은 장치 해제 검수 이후 승인된 최대 2키부터 허용한다.
- 입력 간격·횟수·키 유지 시간·취소 조건을 행동 정의에 포함한다. 목표가 없거나 기대 상태가 사라지면 무작정 스킬을 연타하지 않는다.
- 실행 중 안전 확인은 모델 응답을 기다리지 않는다. 포커스·장치·중단 신호를 확인하는 경로와 DB·모델 작업을 분리한다.
- 적·클리어·사망 등 게임 의미는 GPT가 정의한 관찰 근거와 조건으로 취급한다. 새 게임 상황에 대한 결정이 필요하면 다음 짧은 구간 전에 GPT로 돌아간다.
- 빠른 지역 확인은 필요한 화면 영역과 제한된 주기로 수행한다. 전체 화면 고속 캡처를 상시 실행하여 UI·메모리를 압박하지 않는다.

이 계층은 원각·악귀문 전투 알고리즘을 복사하거나 공유하지 않는다. 필요한 동적 인식·추적이 실제로 구현되지 않았다면 빠른 전투가 완성됐다고 표시하지 않는다.

## 11. GPT 판단 대기 줄이기

| 지연 요인 | 개선 | 유지해야 할 검사 |
| --- | --- | --- |
| 익숙한 구간에서도 반복되는 모델 호출 | 확인된 행동 정의를 지역 실행 | 시작·단계·종료 조건 |
| 길어진 전체 경험 전달 | 관련 경험 5~10개와 요약 중심으로 조회 | 근거 원문을 다시 열 수 있는 연결 |
| 실행기·도구 준비 반복 | GPT 플레이 전용 연결 유지·재사용 | 계정·도구 권한·실행기 호환성 |
| 같은 상황을 매번 처음부터 설명 | 현재 단계·목표·전략·최근 결과를 간결하게 구성 | 목표 변경·환경 변경 시 무효화 |
| 불필요한 화면·긴 대기 | 필요한 장면을 이벤트와 변화에 맞춰 제공 | 오래된 화면으로 입력 금지 |
| 모든 작업을 같은 수준으로 판단 | 익숙한 절차와 새로운 전략 판단을 분리 | 판단 생략이 아니라 검증된 범위의 재사용 |

연결 재사용은 이전 턴과 도구 요청이 중단됐음을 확인할 수 있을 때만 허용한다. 재개마다 새 실행 세대를 발급해 취소된 모델의 늦은 명령을 거부한다. 녹화 분석용 연결을 그대로 실시간 제어에 사용하지 않는다. 안전한 연결 재사용을 확인하지 못하면 지연이 생기더라도 새 연결로 시작한다.

모델·추론 설정은 임의로 바꾸지 않는다. 필요하면 현재 계정과 실행기가 지원하는 설정에서 정확도·속도를 비교한 뒤 별도 선택 사항으로 도입한다. 추론을 줄인 결과 오판이 늘어나는 경우 되돌린다. 네트워크와 모델 응답 시간을 0으로 만들 수 있다고 약속하지 않는다.

측정값은 화면 취득, 경험 조회, 모델 준비, 모델 응답, 도구 왕복, 입력 전송, 게임 화면 전환을 분리한다. 같은 환경에서 최초 실행과 재도전의 중앙값·느린 구간을 비교하고 실패도 포함한다. 게임의 원래 쿨타임을 모델 지연으로 오해하거나 성공률을 버리고 속도만 최적화하지 않는다.

## 12. 영구 저장 구조

```text
%LOCALAPPDATA%/WinCro/gpt_play_memory/
  experience.db
  evidence/<task_id>/
  behaviors/<task_id>/<behavior_version>/
  exports/<task_id>/
  backups/
```

계획하는 논리 테이블은 `tasks`, `goal_revisions`, `environments`, `sessions`, `attempts`, `observations`, `action_receipts`, `strategies`, `hypotheses`, `behaviors`, `behavior_runs`, `checkpoints`, `plan_candidates`, `verification_runs`다. 기록은 작업·시도·버전 ID로 연결하고 삭제 연쇄가 원본 경험까지 지우지 않도록 한다.

SQLite 트랜잭션과 영구 파일의 무결성 확인을 사용한다. DB에 파일 경로만 남고 실제 근거가 없는 상태를 성공 저장으로 인정하지 않는다. 기록 저장은 모델·저장 작업자에서 수행하고 UI 스레드와 긴급 중지 경로를 DB 잠금으로 막지 않는다.

스키마 버전을 기록하고 변경 전 검증 가능한 백업을 만든다. WAL 사용 중인 DB를 파일 하나만 복사해 백업했다고 하지 않는다. 손상이나 마이그레이션 실패 시 기존 DB를 지우거나 빈 DB로 바꿔 성공 처리하지 않는다.

공간과 메모리는 제한한다. 초기에는 기존 세션의 600장·128MB 제한을 유지하고 경험 저장소에는 별도 용량 한도를 둔다. 한도 도달 시 새 수집을 일시정지하고 사용자에게 알린다. 기존 경험·실패 근거를 몰래 삭제하여 계속 실행하지 않는다. 데이터 원본은 로컬에 보관하며 GPT 판단 시 필요한 자료가 모델에 전달됨을 안내한다.

## 13. 입력과 기록의 일관성

외부 게임 입력과 디스크 저장을 하나의 원자 트랜잭션으로 묶을 수는 없다. 다음 순서와 불확실 상태를 사용한다.

1. 실행할 요청과 버전·근거를 입력 전 기록한다.
2. 작업 권한·화면·장치·입력 예산·실행 세대를 다시 확인한다.
3. 입력을 전달하고 장치 접수·완료·해제 상태를 기록한다.
4. 새 화면에서 실제 결과를 확인한다.
5. 결과가 확인된 경우에만 구간 성공이나 게임 성공을 기록한다.

2~4 사이에 앱이 죽거나 응답이 끊기면 요청을 `불확실`로 보존한다. 저장돼 있다는 이유로 자동 재전송하지 않는다. 특히 입장·보상·제작처럼 중복 실행의 영향이 큰 동작은 현재 화면의 결과 확인을 먼저 한다.

입력 전 저장 실패면 입력하지 않는다. 입력 후 저장 실패면 새 입력을 중지하고 이미 수행했을 수 있는 동작을 표시한다. 긴급 중지는 저장 완료를 기다리지 않고 먼저 새 입력 차단과 장치 해제를 수행한다.

## 14. 종료와 재시작 후 이어가기

정상 종료는 새 입력 차단, 모델·이전 도구 요청 무효화, Arduino 해제, 장치 결과 확인, 체크포인트 저장 순서로 처리한다. 앱 강제 종료와 전원 차단은 같은 순서를 보장하지 못하므로 장치 자동 해제와 불확실 요청 복구를 별도로 검증한다.

체크포인트에는 작업·목표·환경·전략·시도 ID, 마지막으로 확인한 단계, 미완료 입력, 다음에 확인할 사항을 넣는다. 저장했던 HWND·PID·이전 화면을 현재 상태인 것처럼 복구하지 않는다. 눌린 키를 복구하지 않는다.

재시작 후 절차는 다음과 같다.

1. 사용자가 기존 경험을 선택하고 `이어하기`를 누른다. 앱 실행만으로 게임 입력을 시작하지 않는다.
2. GPT 연결, 선택 창, Arduino 연결·기능·해제 상태를 다시 확인한다.
3. 새 실행 세대를 만들고 현재 화면을 관찰한다.
4. GPT가 저장된 체크포인트와 실제 상태의 차이를 판단한다.
5. 이미 입장했거나 사망했거나 NPC 위치가 달라졌다면 현재 상태에 맞는 복구부터 진행한다.
6. 미확인 필수 조건은 질문하고, 확인된 단계부터 재개한다.

이전 시도가 종료되지 않았으면 `결과 미기록/미완료`로 표시한다. 패배나 성공을 추측하지 않는다. 같은 작업을 여러 인스턴스가 동시에 수정·실행하지 못하게 실행 소유권과 작업 잠금을 둔다. 중지된 작업의 정상적인 장치 복구까지 영구 차단하는 잠금은 허용하지 않는다.

## 15. 중간 명령과 질문

F10은 새 입력을 차단하고 기존 실행·장치 해제를 확인한 뒤 WinCro 명령창을 연다. 명령을 작성하는 동안 게임 자체가 멈추는 것은 아니다. F11 일시정지, F12 긴급 중지는 유지한다.

사용자 명령은 원문과 적용 버전을 저장한다. 단순 설명과 목표·허용 범위 변경을 구분하되, 불분명하면 보수적으로 기존 자동 실행·검수의 재확인을 요구한다. 이전 경험은 지우지 않고 과거 버전으로 남긴다. 변경 전 검수 성공으로 변경 후 플랜을 등록하지 않는다.

GPT는 화면으로 판단 가능한 평범한 재도전마다 질문하지 않는다. 부활·퇴장 방식이 불명확하거나, 유료 선택·중요 소모품·권한 문제가 있거나, 반복 실험으로 확인하지 못하는 필수 규칙이 있을 때 질문한다. 답변은 해당 작업의 권한과 경험에 반영하고 현재 화면부터 재관찰한다.

## 16. GPT 플레이 UI

GPT 플레이 내부에 `플레이`, `경험 기록`, `플랜 검수`를 둔다. 기존 화면녹화·동작분석 탭과 플랜 편집기는 유지한다. 화면 상단의 실행 상태·개입·중지 접근성은 탭과 스크롤 위치에 관계없이 확보한다.

| 화면 | 사용자에게 표시할 내용 |
| --- | --- |
| 플레이 | 대상 창, 목표, 새 경험/이어가기, 실제 시도·단계, 이번 전략 변경, Arduino 상태, 실행 로그 |
| 경험 기록 | 작업·시도별 결과, 도달 단계, 사용한 전략, 관찰 사실, 원인 후보, 다음 실험, 주요 장면 |
| 재사용 구간 상세 | 시작·종료 조건, 실행 내용, 버전, 성공·실패·기술 오류, 적용 환경, 재검증 이유 |
| 플랜 검수 | 후보 버전, 행동·조건 대응표, 독립 재생 결과, 미지원 동작, 저장·재로딩 결과 |

진행 정도를 알 수 없는데 1~100%를 임의 증가시키지 않는다. 현재 단계와 실제 시도 수, 마지막 진행 후 경과를 표시한다. 성공률에는 확인된 게임 결과만 포함하고 기술 오류·중단·미완료 수를 따로 보여준다.

UI는 저장소를 매 틱 동기 조회하지 않는다. 배경 조회와 변경 알림으로 갱신하고 목록을 가상화·페이지 처리한다. 로그는 증분 갱신하고 사용자가 과거 행을 보고 있으면 강제로 맨 아래로 이동시키지 않는다. 새 데이터 때문에 선택 행·스크롤·입력 중 명령이 사라지지 않게 한다.

## 17. 최종 플랜의 재현성

성공했던 입력을 그대로 나열하는 것이 아니라, GPT가 목표와 규칙을 이해하고 근거를 대조해 행동·조건·복구를 작성한다. 탐색 중 불필요했던 왕복·실패·모델의 생각 대기시간을 정상 작업의 필수 행동으로 복사하지 않는다.

가장 중요한 원칙은 학습, 빠른 재사용, 독립 검수, 최종 재생이 같은 버전의 행동 의미를 사용하도록 하는 것이다. 별도 검수 어댑터에서만 시간을 지키고 실제 플레이 모드에서는 다른 시간으로 키를 보내면 검수 자체가 무효다.

최종 행동 정의에는 입력 종류·키·유지 시간·중첩·반복, 이미지·영역·인식 조건, 단계 전환·성공·실패·복구, 모든 한도와 버전을 포함한다. 조건 분기와 입력 시간이 기존 플랜에 정확히 표현되는지 생성 전에 검사한다.

| 출력 종류 | 허용 조건 |
| --- | --- |
| 일반 플랜 | 기존 실행 형식으로 의미를 보존할 수 있고 실제 플레이 경로에서 검수됨 |
| 새 GPT 전용 행동 플랜 | 기존 형식에 없는 제한된 행동 정의가 필요하며 명시적인 신규 실행 유형·동일 실행기로 검수됨 |
| GPT 연결 필요 플랜 | 실행 중 새 상황의 GPT 판단이 필수임을 표시하고 연결 ON을 실행 조건으로 검증함 |
| 미완료 후보 | 필수 규칙·입력·분기를 표현하거나 검증할 수 없음. 완료 플랜으로 등록하지 않음 |

새 실행 유형이 필요하면 기존 액션의 해석을 바꾸지 않고 신규 타입과 버전으로 추가한다. 기존 플랜은 새 실행기로 자동 전환하지 않는다. 사용자에게는 일반 플랜과 GPT 연결 필요 플랜을 구별해 보여준다. GPT가 계속 필요했던 행동을 GPT 없이 똑같이 실행할 수 있다고 약속하지 않는다.

## 18. 플랜 생성과 검수 순서

1. 목표 달성의 실제 화면 근거와 성공 시도, 적용 환경을 고정한다.
2. GPT가 성공 경로의 의미와 필요한 복구 경로로 후보를 작성한다.
3. 경험에서 플랜으로, 플랜에서 경험으로 번갈아 실제 장면을 다시 열어 대조한다.
4. 입력 시간·동시 입력·이미지·영역·대기·분기·복귀 조건의 누락을 확인한다.
5. 수정하면 후보 버전을 올리고 두 방향 대조와 독립 재생 결과를 무효화한다.
6. 현재 후보의 독립 재생 3회 이상을 초기 게이트로 수행한다. 사람이나 GPT가 살려낸 실행은 독립 성공이 아니다.
7. 최종 승인은 별도 테스트 PC에서 실제 사용자 플레이 경로로 초기 목표 10회 연속 성공과 해당 복구 분기 시험을 수행한 뒤 판단한다. 이 숫자도 모든 미래 상황을 보증하지 않는다.
8. 새 ID로 JSON·근거 자산을 저장하고 실제 모델·실행기로 재로딩해 값과 참조가 같은지 확인한다.
9. 동작분석에 등록한다. 기존 플랜과 재생목록은 자동 덮어쓰기·자동 편입하지 않는다.

동일 후보로 검수했다는 것을 행동 정의·이미지·조건·환경의 해시와 버전으로 확인한다. 새 PC의 해상도·배율·장치가 다르면 별도 호환 검수를 요구한다. 한 PC의 성공을 모든 배포 PC의 성공으로 표시하지 않는다.

## 19. 실행 예산과 실패 정책

초기 실행은 기존 15분·500요청 한도를 유지하고 최대 10시도를 추가하는 안으로 시작한다. 실행 묶음의 실제 원자 입력도 예산에 포함한다. 한도가 끝나면 경험을 보관하고 일시정지한다. 새 모델 턴·앱 재시작으로 실행 예산을 몰래 갱신하지 않는다. 사용자가 이어하기를 눌러 새 실행을 허용할 수 있다.

게임에서 진 경우는 허용된 복귀를 확인하고 다음 시도로 진행한다. 입력·저장·해제·권한이 불확실한 경우는 전략 실험을 중단한다. 모든 오류를 무시하며 재생하는 방식은 채택하지 않는다. 사용자에게 원인, 실제 전송 여부, 재개 조건을 구분해 표시한다.

## 20. 구성 요소와 변경 경계

다음은 구현 시 사용할 책임 분리안이며 파일명은 구현 착수 시 확정한다.

| 구성 요소 | 책임 |
| --- | --- |
| experience_store | 작업·시도·근거·전략·체크포인트의 영구 저장·조회·마이그레이션 |
| attempt_manager | 시도와 단계, 결과 분류, 재도전 예산 |
| experience_context | GPT에 전달할 관련 경험과 사용자 지시 구성 |
| behavior_schema | 행동·조건·입력 시간·버전의 공통 정의와 검증 |
| behavior_executor | 정의된 짧은 실행과 확인·취소. 기존 특화모드와 분리 |
| play_runner | GPT 전용 연결·턴·세대·권한과 취소 |
| Arduino 전용 확장 | 시간 입력·동시 입력·생존 확인·자동 해제 |
| 경험 UI | 비동기 목록·상세·근거·검수 표시 |
| plan_compiler | 행동 의미를 보존하는 새 플랜 생성과 지원 여부 검사 |

GPT 도구는 선택한 작업 안의 경험 조회·시도/결과 기록·행동 정의 작성·제한된 실행만 제공한다. 임의 파일·다른 작업 수정·셸·무제한 입력 도구를 열지 않는다. 녹화 초안 도구 목록은 확장하지 않는다.

## 21. 단계별 구현과 통과 조건

| 단계 | 구현 | 다음 단계로 넘어가는 조건 |
| --- | --- | --- |
| 0 | 기준 동작과 지연 측정, 보호 파일·프로필 기록 | 현재 문제와 시험 환경, 변경 금지 범위가 명확함 |
| 1 | Arduino 전용 시간 입력·자동 해제 | 구형 펌웨어 차단, 정상/중지/통신 끊김/PC 종료 시험 통과 |
| 2 | 공통 행동 정의와 짧은 실행기 | 실제 입력 의미·예산·취소가 일관되고 기존 입력에 영향 없음 |
| 3 | 경험 저장·조회·UI | 실제 저장/재로딩, 재시작, 손상·용량·중복 실행 시험 통과 |
| 4 | 시도·결과·전략 비교와 복귀 | 기술 오류를 패배로 잘못 학습하지 않고 실제 복귀 후 재도전함 |
| 5 | 성공 구간 재사용과 GPT 연결 최적화 | 정상 구간 내부 GPT 호출 없이 완료, 예외 시 올바르게 인계됨 |
| 6 | 제한된 동시 입력·전투 실행 | 허용 조합, 장치·입력 자동 해제, 화면 조건 이탈 시험 통과 |
| 7 | 플랜 생성·전체 검수 | 실제 플레이 경로에서 행동 의미·성공·복구·저장 무결성이 확인됨 |

실제 보드가 시간 입력을 지원하지 않는 동안 경험 UI와 저장 시험은 진행할 수 있지만, 실제 이동·전투 개선 완료라고 보고하지 않는다. 동시 입력은 단일 시간 입력의 안전성을 통과하기 전에 활성화하지 않는다.

## 23. 완료 판정과 보고

완료 보고는 구현된 것, 시뮬레이션으로 확인한 것, 실제 장치·게임에서 확인한 것, 남은 미지원 사항을 분리한다. 이전 테스트 개수를 새 기능의 검수 결과로 재사용하지 않는다. 테스트의 건너뜀·경고·간헐 실패도 구분한다.

합격 기준은 데이터를 쌓는 것 자체가 아니다. 기록된 경험이 다음 판단에 실제 반영되는지, 익숙한 구간의 모델 호출이 줄었는지, 재시작 후 다른 상태에서도 안전하게 이어가는지, 최종 플랜이 실제 실행에서 목표와 복구를 재현하는지를 확인해야 한다.

필수 입력·게임 규칙·플랜 표현이 해결되지 않았으면 그 단계를 미완료로 보고한다. 성공 1회나 검수 체크리스트만으로 완벽성을 선언하지 않는다. 기존 플랜·특화모드·인식 경계를 침범해야만 가능해 보이는 구현은 진행하지 않고 독립 구조로 재설계한다.
